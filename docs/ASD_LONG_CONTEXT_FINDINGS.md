## 成本归因

原ASD首token均值约0.486/1.992/4.815秒。以首token均值除以总请求耗时均值，其占比约17.15%/45.22%/60.82%；这是请求边界分解，包含tokenize和首token处理，不是纯GPU预填充份额。

独立回放同一已指定题，Target预填充GPU工作约0.49/1.92/4.70秒；首次Draft forward仅约0.017/0.038/0.071秒。两部分不是同一瓶颈。位置适配只改变Draft q/v权重，既不减少Target预填充工作，也不保证在多示例条件下始终减少后续验证轮数。短零示例训练与长示例输入存在分布差异，是一种合理解释；本轮没有通过额外训练或因果干预证明该解释。

主比较包含engine.generate内的snapshot/tokenize、预填充、生成、同步与文本解码；不含HTTP、排队、请求文件读取或模型加载。四进程模型准备约20.02–20.31秒，各4张编译图，backend约3.34–3.47秒；冷成本保留在warmup.jsonl，不混入正式均值。正式峰42.292GiB，全部8个预检/正式进程cache合计3363660B。9个profiler只保存聚合归属，不发布raw trace，其时间不当作性能计时。

## 下一步建议

优先验证共享示例前缀缓存，目标是减少重复Target预填充。本工作负载中各题共享一段公开示例前缀，适合检查这种优化。成熟方案可参考[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/v0.13.0/features/automatic_prefix_caching/)：复用相同前缀的KV，减少prefill计算；它不直接缩短新token的生成计算。

结合当前DFlash实现，首个小原型只缓存公共前缀的Target KV和Draft所需的选层Target hidden features，命中后计算新问题后缀，沿用原Draft/验证循环。首次Draft约71ms，可暂缓引入Draft KV缓存，优先处理约4.7秒的Target预填充。缓存键需包含模型/tokenizer/数值profile、精确token前缀及特征层选择；每请求ASD预算仍独立。公共示例缓存与用户私有记忆分开，禁止把当前答案写进过去前缀。

这是待验证方案，尚未实现。先检查缓存命中/未命中的token、EOS、预算、KV边界和质量，再计入缓存填充、查找、复制、淘汰及显存成本；FP32分段prefill可能改变舍入，必须与未缓存参考核对。通过单请求检查后再研究成熟serving底座和连续批处理，当前不宣称已有缓存收益。
