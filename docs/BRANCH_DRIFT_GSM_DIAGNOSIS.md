# GSM8K为什么比ASD慢，优先怎样改

2026-10-30：只诊断2026-10-29已发布数据，未新增GPU生成、未改变推理或原评分。

后续已完成[宽度对照与反馈实测](GATE_WIDTH_FINDINGS.md)：GSM反馈版较旧组合快1.44%，仍慢于ASD5.38%；MATH另有正结果。下文保留执行前诊断与建议，不将后续实测混入原924行结果。

**主因是生成路径变长，其次是当前节点分配减少宽度后，节省单轮成本却增加了验证轮数。JS本身不是主要耗时来源。** 第二项的具体宽度机制仍需新对照验证，不将请求wall/轮当作独立Target剖析。

## 尚有一部分可优化的树开销

|自然请求汇总|严格成本树|组合|
|---|---:|---:|
|平均节点|28.26|19.30|
|平均最大树深|9.68|9.68|
|验证轮|315|337|
|总wall|25.034秒|26.021秒|

当前旁支权重qr*(qr/q0)压低低rank候选，平均节点更少、最大深度相近，但多22轮。其较窄的覆盖与轮次增加相符；尚未保存逐轮所有未展开节点的反事实，不能断言每一轮差值都只由宽度引起。

六题中组合与严格树最终token完全相同，组合仍配对平均慢4.02%。因此除了回答路径变长，也存在树结构/检查的额外成本。固定正确性不变时，宽度与轮数的权衡有直接改进依据。

组合本批JS摘要仅0.00681秒，包含它的门控摘要约0.06386秒，远小于净增1.834秒。摘要不是完整验证器分项剖析，但已不支持继续把JS当主瓶颈。

GateTree与GateCap在8题上输出和验证轮数都相同；移除独立regret≤ln4上限不能消除本批慢6.91%的问题。它主要改变了部分未提交旁支的检查。

## 优先解决方式

1. 保持JS、EOS、真实兄弟覆盖和当前token上限，先比较更宽的构树：把固定旁支惩罚1降低，或以0作为接近原成本树分配的对照。恢复覆盖能否减少22轮，比继续微调JS算子更值得验证。固定门槛也不保证新树整条输出的AR一致率单调改善，须同时报告保真和质量。
2. 若固定惩罚对照有效，再做轻量反馈：Target首选频繁落在Draft旁支、严格推进经常提前结束时降低惩罚、增加宽度；主干命中稳定时保持较窄树。使用已经发生的验证反馈，节点上限仍32，计入在线成本；这是下一步建议，尚未实现或测试，不训练复杂未来长度预测器。
3. 对已经复现AR的395token回答，维持该输出就必须完成这些token的计算。按本批总量，要追平ASD总wall，当前汇总吞吐还需约7.6%提升；仅恢复到现有严格树水平也不保证胜出，因为严格树本批仍配对慢ASD3.23%。若无法获得足够的计算效率，GSM可以保留为速度/保真取舍场景，不预设所有数据都应快于ASD。

不能由本批日志可靠预测哪次近似一定会缩短未来回答；此前Run/Utility也未证明这一点。当前更直接的下一步是构树宽度对照，保留已有保真门控，不因这8题事后放宽门槛或修改Target提示。
