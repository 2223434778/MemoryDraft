# MATH-500为什么耗时增加

**主要拖累是一道进入循环并达到长度上限的题目；其余题目还存在较小的计算与路径差异。** 这次只分析已发布日志，不新增GPU生成、不改变评分和原始结果。

原12题逐题配对均值仍为+31.19%；总wall 116.04→150.13秒，净增34.08秒。两种统计口径不同。

## 1. 主要拖累：math500:372

DFlash为824 token/7.81秒，正常EOS且答案90°正确；新版为4096 token/33.47秒，达到上限且未答对。该题新增25.66秒，占12题净新增wall的75.29%。
最终token序列后3000个token存在精确的249-token周期，包含12个完整周期；从第1097个token起，不断重复同一组等式。它反复得到x=140°−y，没有利用已知角收敛到90°。

这是已经提交的最终输出发生推导循环。日志记录正常推进到4096上限，没有显示推理引擎停在同一次调用中。

## 2. 为什么JS没有挡住

该题仅5次近似例外，所选JS累计0.055477，但仍走入循环路径。第一轮例外regret=3.1010，候选/Target首选概率比约4.50%；原ASD按剩余长度归一化的门槛允许了它。

一步后续分布相似，并不约束当前选择对完整推导的影响。每个后续token只要在已改变的上下文下仍为Target贪心，就不再额外扣regret；预算不能自动纠正这条上下文。
最后一次例外位于第1258–1263个token之间，之后至少2833个token没有再接受例外，仍持续循环。停止继续花预算也不会恢复原AR路径。

## 4. 计算本身也有成本，但不是所有token慢31%

总输出12810→16470，增加28.57%；汇总吞吐110.39→109.71 token/s，变化-0.62%。因此总体主要是多写了token。
验证轮1486→1672；每输出token轮数下降12.49%，每轮请求wall摊销增加14.98%，两者大体抵消。

上述为恒等分解：时间比=长度比×每token轮数比×每轮wall摊销比。wall/轮包含prefill和CPU等工作，不能把全部差值归为JS，也不能当成单次Target前向测量。
零例外的math500:224, math500:95, math500:465三题与DFlash输出完全相同；新版较DFlash配对均值-0.21%，较严格树+4.48%。这支持存在构树/检查/额外轮次的小幅组合成本，未支持普遍31%的硬件卡顿。

原表中新版相对原组合的共同128前缀慢5.65%（12题），相对严格树慢2.13%。这部分等生成量成本仍需承认；本轮没有DFlash等128前缀直接对照。

## 5. 改进重点

优先约束当前近似token的分歧强度，例如增加独立于剩余后缀长度的候选/首选概率比下限（等价于regret上限）；它能过滤这里已观察到的高regret例外，但尚未做反事实验证，不能保证该题必然恢复。
再考虑重复周期检测与有计时的纠错/重生成策略。直接把4096上限改短只会更早截断错误答案，不是保持质量的加速。单纯优化JS算子难以解决这道题多写3272token的问题。
